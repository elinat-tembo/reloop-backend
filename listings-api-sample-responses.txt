Reloop Backend API — Sample Responses
======================================
All examples below were captured from real requests against a running
instance of this server (not hand-typed), so shapes/status codes are exact.

PAGINATION (applies to GET /api/listings, GET /api/listings/mine,
GET /api/swaps/incoming, GET /api/swaps/outgoing)
------------------------------------------------------------------
Offset-based, driven by query params (both optional):
  ?page=<n>   default 1, invalid/non-positive values fall back to 1
  ?limit=<n>  default 20, invalid/non-positive values fall back to 20, capped at 100

Every paginated response adds a "pagination" object next to the data array:
{
  "page": 1,
  "limit": 20,
  "total": 7,
  "totalPages": 1,
  "hasNext": false,
  "hasPrev": false
}
Drive Next/Prev buttons off hasNext/hasPrev; request page+1 / page-1 with the
same limit. totalPages lets you render page numbers if you want them later.


LOCATIONS (city/region validation, applies to POST/PUT /api/listings)
------------------------------------------------------------------
city and region are validated as a pair against a curated list (not just
individually) — a mismatched pair is rejected even if both values are
independently real cities/regions. If neither city nor region is sent, no
location validation runs (both stay null). If either is sent, both must be
present and form a valid pair.

const LOCATIONS = {
  "Lusaka Province": ["Lusaka", "Kafue", "Chongwe", "Chilanga"],
  "Copperbelt Province": ["Ndola", "Kitwe", "Chingola", "Mufulira", "Luanshya"],
  "Southern Province": ["Livingstone", "Choma", "Mazabuka", "Monze"],
  "Other Provinces": ["Kabwe", "Chipata", "Kasama", "Solwezi"]
}

400 Bad Request (region missing/unknown)
{ "error": "region must be one of: Lusaka Province, Copperbelt Province, Southern Province, Other Provinces" }

400 Bad Request (city doesn't belong to region, e.g. city="Ndola" with region="Lusaka Province")
{ "error": "city must belong to the selected region" }

Note for frontend: estimatedValue is returned as a STRING (e.g. "45"), not a
number — it's a Postgres numeric column and Drizzle serializes it as a string
to avoid float precision loss. Parse it before doing math. It is NOT
zero-padded to two decimals (a value of 45 comes back as "45", not "45.00").

SWAP REQUESTS — /api/swaps
=====================================
status is one of: "pending", "accepted", "rejected", "expired", "cancelled"

POST /api/swaps
----------------
Body: { "requestedItemId": 3, "offeredItemId": 2 }
fromUserId = req.user.id, toUserId = owner of requestedItemId (set server-side).

201 Created
{
  "swapRequest": {
    "id": 1,
    "fromUserId": 5,
    "toUserId": 6,
    "requestedItemId": 3,
    "offeredItemId": 2,
    "status": "pending",
    "createdAt": "2026-09-12T07:24:19.082Z",
    "updatedAt": "2026-09-12T07:24:19.082Z"
  }
}

400 Bad Request (missing fields)
{ "error": "requestedItemId and offeredItemId are required" }

400 Bad Request (requesting your own item)
{ "error": "You cannot request your own item" }

403 Forbidden (offered item isn't yours)
{ "error": "You do not own the offered item" }

404 Not Found (offered item doesn't exist)
{ "error": "Offered item not found" }

404 Not Found (requested item doesn't exist)
{ "error": "Requested item not found" }

409 Conflict (offered item not available)
{ "error": "Offered item is not available" }

409 Conflict (requested item not available)
{ "error": "Requested item is not available" }

PATCH /api/swaps/:id/accept
-----------------------------
Only toUserId can accept, only while status is "pending".
Side effects (all applied atomically in one batch):
  - this request -> status "accepted"
  - requestedItem and offeredItem -> availability "unavailable"
  - every OTHER still-pending request touching either item (as
    requestedItemId OR offeredItemId, in either role) -> status "expired"

200 OK
{
  "swapRequest": {
    "id": 1,
    "fromUserId": 5,
    "toUserId": 6,
    "requestedItemId": 3,
    "offeredItemId": 2,
    "status": "accepted",
    "createdAt": "2026-09-12T07:24:19.082Z",
    "updatedAt": "2026-09-12T07:24:49.197Z"
  }
}

403 Forbidden (not the recipient)
{ "error": "Only the recipient of this swap request can accept it" }

404 Not Found
{ "error": "Swap request not found" }

409 Conflict (not pending anymore)
{ "error": "This swap request is no longer pending (status: accepted)" }

Example of a competing request auto-expired as a side effect of the accept above
(same requestedItemId, different offeredItemId/sender):
{
  "swapRequest": {
    "id": 2,
    "fromUserId": 7,
    "toUserId": 6,
    "requestedItemId": 3,
    "offeredItemId": 4,
    "status": "expired",
    "createdAt": "2026-09-12T07:24:40.488Z",

  }
}

CHAT — /api/swaps/:swapId/messages

from a live run (the Chat module was built without live verification, per
instruction). Shapes/status codes should match exactly, but timestamps/ids

Messages are immutable — send-only, no edit/delete endpoints. Only the
fromUserId or toUserId of the swap request can send or view its messages.

{ "error": "Swap request not found" }

with id greater than that value — poll with the highest id you've already

SYSTEM MESSAGES (in swap chat history)
=====================================
NOTE: constructed from the controller logic, not live-captured.

System messages are inserted automatically alongside the swap-status actions
below. They appear in GET /api/swaps/:swapId/messages (and the admin
equivalent) mixed in with regular user messages, oldest to newest.
senderId is null and isSystem is true — render these differently from a
normal chat bubble (e.g. centered system-style text) rather than attributing
them to a user.

Example entries:
{
  "id": 5,
  "swapRequestId": 1,
  "senderId": null,
  "isSystem": true,

  "id": 6,
  "swapRequestId": 2,
  "senderId": null,
  "isSystem": true,
  "content": "This swap request expired because one of the items was used in another accepted swap.",

{
  "id": 7,

  "senderId": null,
  "isSystem": true,

  "createdAt": "2026-09-16T10:05:00.000Z"
}
{
  "id": 8,
  "swapRequestId": 4,
  "senderId": null,
  "isSystem": true,

DELETE /api/admin/listings/:id
----------------------------------
Force-deletes regardless of pending swap requests (bypasses the regular
owner-delete 409 block). Any pending swap request touching this item (as
requestedItem OR offeredItem) is set to "cancelled_by_admin", gets a system
message, and the OTHER item in that swap is set back to "available".

200 OK
{
  "message": "Listing deleted successfully",
  "cancelledSwapRequests": 1
}

404 Not Found
{ "error": "Listing not found" }
